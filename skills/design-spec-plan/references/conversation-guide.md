# Conversation Guide

Topics for the planning conversation, in a natural order. Each says what to find out, what it changes, the default, and when to skip. The questions are prompts, not a script.

## Contents
1. Starting
2. Topics
3. Recommending visual source
4. The reflect-and-confirm message
5. After the reply

---

## 1. Starting

The overview page (`overview.md`) is the front door when someone invokes the skill with nothing else. When they reply "start my spec plan", begin the walkthrough straight away: no second welcome. Say one friendly line ("Great. A few questions at a time, and I'll suggest a default for each."), then ask the first topic.

If they paste material instead, skip the overview and say what you read.

### Walkthrough path

Ask the topics in section 2 in order, two or three questions at a time, each with your recommended default. Keep it light and let them answer in a line. After the last topic, go to the reflect-and-confirm message (section 4).

## 2. Topics

### A. Context
- **Find out:** what the project is, who it serves, brand or visual direction, known constraints, assumptions and risks, and any **time-box** (for example "three weeks").
- **Changes:** the context block, scope recommendation, and how thin the first slice should be.
- **Skip when:** already stated.

### B. What you're building
- **Find out:** design system only, or experience specs (screens and flows) too? New, or changing something existing? One product, or a system that several products will share? End product: a prototype, a concept, or something engineering will build from?
- **Changes:** which folders exist; whether the scaffold needs `experience/`; whether the structure should allow multiple experiences later.
- **Default:** if the brief mentions screens or user journeys, recommend experience specs too.

### C. Inputs
- **Find out:** Figma files, a prototype or code, existing docs or a PRD, any existing specs. Where they live.
- **Changes:** the input strategy and the source chips on the card.
- **Never:** read values from these into the plan. Links only.
- **Figma links: a light scan, not a read.** List every page with its top-level sections, and the variable collections with their modes, as `../design-spec-authoring/references/connections.md` describes ("Reading a Figma file"). The scan informs breadth, themes and the scaffold; it never puts values or component lists into the plan. If the read-only tools can't list every page or the variable modes, use a read-only script and say so in "What I heard" (`connections.md`, "Read-only scripts are reads"). If pages or modes still can't be read, say so there too and ask the designer to name them, rather than asking what the file contains.

### D. Scope and scale (light)
- **Find out:** roughly what kinds of things are involved: forms, modals, navigation, data views, bespoke 2D/3D or video content (scene components), layouts and breakpoints. Whether more than one theme or brand is needed.
- **Token tier:** recommend **2-tier** unless the designer has a reason (see `../design-spec-authoring/references/best-practices.md`, "Tiers").
- **Themes or brands:** light and dark modes count as `multiple`; 2-tier tokens still fit (3-tier is for multiple brands, or themes beyond light and dark; see "Tiers"). If a Figma file is given, take the answer from its variable modes (the scan above). With no Figma and nothing in the input, default **one**. If Figma exists but its modes couldn't be read, ask; never default to one on a failed read.
- **Changes:** which foundation files to recommend and which spec types appear in the scaffold.
- **Components:** ask "Where do the components come from? Designed for this product (custom), an outside library such as Material 3 or shadcn/ui, your organization's existing design system, or a library with custom components added on top?" Default **custom**. If not custom, follow up: which library, its pinned version (what engineering installs), where its docs and Figma kit live, and its `base` where the library offers one (shadcn/ui: Base UI, Radix or React Aria; if the designer doesn't know yet, say authoring will ask). These follow-ups may be grouped under one question. If the library has its own motion, also ask: "Which parts of its motion should the product use: timing values, transition patterns, its components' built-in animation, its reduced-motion behavior, springs?" Recommend the answers in `../design-spec-authoring/motion/motion.md` ("Using a component library"): the first three, this system's reduced motion, and no springs unless the product wants expressive motion.
- **Platform fit:** check that the library suits the platform the product targets. A web library (such as shadcn/ui) for a native app is a blocking question at the reflect stop, not a detail.
- **Generative UI:** ask "Will any part of the product UI be generated by AI at runtime?" Default **no**. A yes means AI-ready components (Generative use) and a host with Generated content (an AI model choosing from approved components, for example an assistant answering in chat with cards), and an assistant voice in `intent`. Only choosing from approved components is supported; composing whole layouts or generating new UI code at runtime isn't.
- **Not asked:** the component list.

### E. Spec approach
- **Guidance preference:** *guided* (step by step, authoring checkpoints after each spec) or *self-directed* (loose reference; the designer drives). Default: guided for anyone new to specs.
- **Endpoint:** **Local markdown** or **Documentation platform**. If a platform, which one and where. If local, which project folder: the spec set is created as `[project folder]/design/`, holding every spec and, at its root, `spec-plan.md`. The project folder must sit outside any code repository (`../design-spec-authoring/references/endpoints.md`, "Outside code repositories").
- **Visual source:** `figma` or `spec-only` (see section 3).
- **Changes:** the Project context table, scaffold (local adds `AGENTS.md`; a platform uses its index page), and the handoff prompt.

### F. Team and toolkit
- **Find out:** solo or several designers? Who else participates (PM, engineers)? Which tools they have (Claude, Cursor, Figma, others).
- **Changes:** the "Working together" line and the recommended tools.
- **Default:** if more than one designer, recommend sharing the project (a shared Claude project, or the shared folder in Cursor) and naming one owner for the plan.
- **Handoff to engineering:** the spec set lives outside engineering's code repositories (`../design-spec-authoring/references/endpoints.md`, "Outside code repositories"). Engineers and their coding agents read `ready` specs (and Ready for dev in Figma, in `figma` mode) from the endpoint. Say this when engineers are involved.

## 3. Recommending visual source

| Situation | Recommend |
|---|---|
| A Figma file exists (or will, with approved visuals) | `figma` |
| No Figma; the designer will build a prototype directly from specs | `spec-only` |
| Unsure | `spec-only`, noting visuals can migrate to Figma later by replacing each spec's Visual section with Figma node references |

State the recommendation with a reason and confirm it.

## 4. The reflect-and-confirm message

After reading the input, send one message and stop. Don't produce the plan yet.

```
**What I heard**
- [At most 8 short lines. Merge related points. Inferred items marked "(assumption)".]

**What I recommend**
- Visual source: [figma | spec-only], because [reason]
- Endpoint: [Local markdown: specs in `[project folder]/design/` | Documentation platform: platform and root], because [reason]
- Guidance: [guided | self-directed], because [reason]
- Token tier: [1|2|3]-tier, because [reason]; themes: [one | multiple]
- Breadth: [design system | experience | both] [; first slice and what's deferred, if time-boxed]
- Components: [custom | third-party | internal | mixed: library and version], because [reason]
- Library motion: [parts used; parts kept as this system's] (only when the library has its own motion)
- Generative UI: [none | yes: hosts], because [reason]

**A few questions** (at most 6, one point each; library follow-ups may be grouped under one)
1. [Missing or ambiguous plan-level item]
2. [...]
Anything above I got wrong, or want to change?
```

When a library is used, include the platform-fit check (section 2, topic D): a library that doesn't suit the platform is a blocking question. Keep it short. Don't ask about individual components or Figma contents beyond the light scan; authoring covers those. Don't say unresolved rules will go into specs; they are open points for authoring. If nothing is missing, the questions list can be just the last line. Wait for the reply.

## 5. After the reply

1. Apply the corrections.
2. If a blocking gap remains, ask one more short batch. Otherwise, build the scaffold (`scaffold-guidance.md`) and produce the outputs in the next message.
