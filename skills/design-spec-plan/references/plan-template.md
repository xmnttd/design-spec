# Plan Template

The plan is a **one-page card**, like a postcard: scan it in 30 seconds. `spec-plan.md` is the card plus a tiny "For authoring" block. Show the card in chat exactly as saved.

## Length limits (hard)

- Whole card: about **80 lines**, including the scaffold block. If it runs over, cut words, not sections.
- **Context table cells: 12 words or fewer.** No sentences with clauses; fragments are fine.
- **Assumptions: at most 3. Risks: at most 2.** Each 10 words or fewer.
- **Steps table: six rows, notes 8 words or fewer.** Never more than six steps.
- **No** "Decisions and assumptions" section, **no** "Recommended foundation files" section, **no** prose paragraphs. Reasons live in the chat confirmation, not the file.
- **For authoring:** at most 4 bullets, each a question of 15 words or fewer.

Leave out any row you have nothing real for, except Components and Generative UI, which always appear (with their defaults if nothing else applies). No placeholders, no "TBD", no "(named; link to be shared)" inside values.

---

## No front matter

Don't put YAML front matter at the top. Viewers render it as a long property list above the title and it repeats the Project context table. **The Project context table is the single source**: authoring reads it. So each parseable row starts with its keyword in backticks, then at most 8 words:

| Row | Keyword values |
|---|---|
| Breadth | `design-system` · `experience` · `both` |
| End product | `prototype` · `concept` · `engineering-build` (for the team's reference; authoring doesn't act on it) |
| Guidance | `guided` · `self-directed` |
| Visual source | `figma` · `spec-only` |
| Endpoint | `local` (then the full `design/` path) · `documentation platform: <name>, <root>` |
| Token tier | `1` · `2` · `3` |
| Themes | `one` · `multiple` |
| Components | `custom` · `third-party: <name> <version>` · `internal: <name> <version>` · `mixed: <name> <version> + custom` (`<version>`: the pinned version, what engineering installs) |
| Motion | `this system's` (the library has no motion of its own) · `uses: <parts> · keeps: <parts>` (no library name; it's in Components) |
| Generative UI | `none` · `yes: <hosts>` |

Keep the row labels exactly as in the card (below). Team lists a count and roles, no names. Anything missing or pending goes in the card ("Before authoring"), not in a value.

## Card

### 1. Header
`# Spec Plan: [Project]` is the very first line of the file. Then one italic line: generated by `design-spec-plan`, date (and "supersedes the plan of [date]" for a re-plan).

**Re-plan only:** one line under it, `**What changed:** [item] · [item] · [item]`, at most three items of 10 words or fewer. A library adopted or changed, or generative UI added, is named here.

### 2. Project context
Two-column table with an empty header row, only the rows that apply: **What · Who for · Breadth · End product · Guidance · Visual source · Endpoint · Token tier · Themes · Components · Motion · Generative UI · Team · Time-box · Assumptions · Risks**. Components (default `custom`) and Generative UI (default `none`) always appear. Motion appears only when a library is used.

Then one line of source chips: `Figma: name` · `PRD: name` · `Brief: name`, plus `Docs: <library> <version>` · `Figma kit: <name>` when a library is used (only inputs actually given). If the designer said there are no other inputs, add the chip `No other inputs`, so authoring doesn't ask again.

If any named input hasn't been shared yet, add one line: **Before authoring:** share [the Figma link, the PRD].

### 3. Scaffold
A code block of the folder tree (`scaffold-guidance.md`). One line under it: *Filenames are examples; authoring builds the real list. Visual values never live here.*

**Re-plan only:** the tree shows the folders plus only the files added, moved or retired, each marked: `(new)`, `(moved from [folder])`, `(retired)`.

If there is a time-box, one line each: **First slice:** [files or spec types, including the foundations its screens depend on] · **Deferred:** [short list].

### 4. Steps and skills
Six steps, three phases, from `process-steps.md`, with the Design row for the plan's visual source: the small phase line (`Architect → Author → Validate → back to 1`), then the 6-row table. Then at most two short lines:
- Start where your project is; re-run this plan only for a big change.
- Working together *(only if more than one designer)*: share the project; one owner for `spec-plan.md`.

### 5. Next step
The go-time prompt in a code block (`handoff-prompt.md`).

---

## For authoring (file only, below the card)

At most four bullets: open questions authoring will need answered (for example whether a map is interactive). Questions only, one line each. These are known unknowns, not decisions; they never become TBDs in specs.
